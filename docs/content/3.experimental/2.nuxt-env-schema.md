---
title: Nuxt environment schemas
description: Build without deployment values and validate injected config at runtime.
---

The experimental environment schema source reads a committed `.env.example`. It generates types during `nuxt prepare` and validates deployment values at server startup. It requires Node.js 22 or later during preparation and build.

```ts
export default defineNuxtConfig({
  modules: ['nuxt-safe-runtime-config'],
  safeRuntimeConfig: {
    experimental: { envSchema: '.env.example' },
  },
})
```

Do not combine this option with `$schema`. The experiment enables runtime validation and skips build validation by default. `validateAtRuntime: false` is rejected. Leave `onError` at its default, `throw`, to reject invalid deployments.

```dotenv
# Database connection injected when the server starts.
# @type=url @example="postgresql://example.test/database"
NUXT_DATABASE_URL=

# API credential injected when the server starts.
# @type=string(minLength=16)
NUXT_API_SECRET=

# @public @type=boolean
NUXT_PUBLIC_REPLAY_ENABLED=false

# @public @type=number(min=0, max=1)
NUXT_PUBLIC_SAMPLE_RATE=0.1

# @public @type=enum(debug, info, warn, error)
NUXT_PUBLIC_LOG_LEVEL=info

# @optional @type=number
NUXT_REQUEST_LIMIT=
```

Assignments declare real defaults. `@example` is documentation only. `KEY=` declares no default. Review placeholder assignments before enabling this option on an existing example file. The supported syntax and conversion rules are defined in the [environment schema profile](./env-schema-profile).

```ts
const config = useSafeRuntimeConfig()
config.databaseUrl // string
config.public.replayEnabled // boolean
config.public.sampleRate // number
config.public.logLevel // 'debug' | 'info' | 'warn' | 'error'
config.requestLimit // number | undefined
```

Types come from declarations, without reading local `.env` values. Values become typed outputs after runtime validation. `process.env` retains its normal `string | undefined` types. Process-injected string inputs such as `00123`, `1e3` and `false` retain their exact spelling at startup and when the validation middleware creates a fresh Nitro request config. Existing request-scoped config uses its own values; spelling already lost by the runtime's parsing cannot be recovered without its original source. Invalid typed overrides fail instead of restoring a valid default.

## Deployment

Build with the schema file present and deployment variables absent. Inject canonical `NUXT_*` variables when starting the built server. The same artifact can start with different credentials and public config without rebuilding.

The schema owns its declared runtime config paths. Build-time values and handwritten defaults at those paths do not replace the defaults declared in the schema. This prevents inherited build credentials from becoming artifact defaults. Real assignment defaults are bundled, so put credentials in the deployment environment and keep their assignments blank.

Private fields stay in server config. Browser fields require both `NUXT_PUBLIC_` and `@public` or `@sensitive=false`. A private key marked `@public` remains private; the annotation cannot override Nuxt's prefix rules.

## Nested config

Keys map to flat camelCase fields by default. `NUXT_DATABASE_URL` becomes `databaseUrl`. Explicit paths preserve existing nested application APIs:

```ts
safeRuntimeConfig: {
  experimental: {
    envSchema: {
      file: '.env.example',
      paths: {
        NUXT_PUBLIC_POSTHOG_REPLAY_SAMPLE_RATE: 'public.posthog.replaySampleRate',
      },
    },
  },
}
```

Each path must convert back to exactly its declared Nuxt environment key. Reserved keys, duplicate paths, scalar/object collisions and visibility changes fail with source locations. The schema file is watched and changes restart Nuxt development setup.

Objects, arrays, transforms, cross-field conditions and dynamic defaults are outside this experiment. Keep `$schema` for those requirements.
