Runtime config has two moments where it can be wrong. At build time it holds what `nuxt.config.ts` says. When the server starts, Nitro replaces those values with any matching `NUXT_*` environment variables. Validate at the moment whose values you actually deploy.

## Build validation

Build validation is the default. It runs your schema against the resolved `nuxt.config.ts` values during `nuxt dev` and `nuxt build`, before anything ships.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
  },
})
```

Use it when the values in `nuxt.config.ts` are the values you deploy, for example when CI reads secrets from the environment while building. Nothing about validation runs in production.

It cannot see variables that are only set when the server starts. A build that passes with `databaseUrl: ''` replaced later by `NUXT_DATABASE_URL` tells you nothing about that variable.

## Runtime validation

Runtime validation checks the config the server actually starts with, after Nitro applies `NUXT_*` overrides.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
    validateAtRuntime: true,
  },
})
```

With runtime validation on:

1. A Nitro plugin validates `useRuntimeConfig()` on cold start, before your own server plugins.
2. Overrides are [coerced](/guide/environment-overrides) to the types the schema expects, so `NUXT_PORT=3000` becomes `3000`.
3. A middleware prepares each request's config before handlers run, so `useSafeRuntimeConfig(event)` returns validated values.
4. Validated values are written back into runtime config, so Nuxt serializes them into the client payload.

Build validation turns off by default when runtime validation is on, because build-time values are placeholders the environment replaces. The build no longer needs real secrets.

An inline `$schema` is converted to JSON Schema at build time and validated with [@cfworker/json-schema](https://github.com/cfworker/cfworker/tree/main/packages/json-schema), which also runs on edge runtimes. Your schema library is not bundled. A schema with transforms has no JSON Schema form; [put it in a schema module](/guide/environment-overrides#transform-values-with-a-schema-module) and the server runs it as written.

## Both

Turn build validation back on when the build has real values and you also want to catch what the deployment changes:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
    validateAtBuild: true,
    validateAtRuntime: true,
  },
})
```

## When validation fails

`onError` decides what a failure does, at build and at runtime:

| `onError` | At build | At runtime |
| --- | --- | --- |
| `'throw'` (default) | Logs the issues and stops `nuxt dev` or `nuxt build` | Stops the server for a synchronous schema; rejects requests for an asynchronous schema or an invalid event config |
| `'warn'` | Logs the issues and continues | Logs the issues and continues |
| `'ignore'` | Continues silently | Continues silently |

Keep `'throw'` in CI and production. `'warn'` is for migrating an app whose config does not pass yet.

Build validation runs your schema library and lists each issue with its path:

```txt
[safe-runtime-config] Validation failed!
  1. databaseUrl: Invalid type: Expected string but received undefined
  2. public.apiBase: Invalid URL: Received "localhost"
```

Runtime validation of an inline schema reports JSON Schema errors with their JSON Pointer:

```txt
[safe-runtime-config] Runtime validation failed: #: Property "databaseUrl" does not match schema., #/databaseUrl: String does not match format "uri".
```

A schema module reports in the first format, since the server runs your library.
