Environment variables are strings. Nitro 3 passes them into runtime config unchanged. Nitro 2 parses some of them, so `NUXT_FLAG=1` arrives as the number `1` and `NUXT_LABEL=123` as `123`. Either way, a schema that says `boolean()` would reject `NUXT_PUBLIC_REPLAY_ENABLED=false`.

Everything on this page applies with `validateAtRuntime: true`.

## Coercion

Before validating, the module converts each value the schema would reject into the type it expects:

| Schema expects | Converted values |
| --- | --- |
| `boolean` | `'true'`, `'false'`, `'1'`, `'0'` in any case, and `1`, `0` |
| `number` | numeric strings such as `'0.5'` or `'3000'` |
| `integer` | integral strings such as `'3000'` |
| `string` | integers and booleans that Nitro 2 parsed, such as `123` or `true` |
| array or object | JSON strings such as `'["email","github"]'` |
| enum or literal | strings that convert to one of the allowed values |

A plain schema is then enough:

```ts [nuxt.config.ts]
import * as v from 'valibot'

export default defineNuxtConfig({
  runtimeConfig: {
    public: { replayEnabled: false, sampleRate: 0.1 },
  },
  safeRuntimeConfig: {
    $schema: v.object({
      public: v.object({
        replayEnabled: v.boolean(),
        sampleRate: v.number(),
      }),
    }),
    validateAtRuntime: true,
  },
})
```

Start the server with `NUXT_PUBLIC_REPLAY_ENABLED=true NUXT_PUBLIC_SAMPLE_RATE=0.4`, and `useSafeRuntimeConfig().public` is `{ replayEnabled: true, sampleRate: 0.4 }` on the server and in the client payload.

The rules are conservative:

- A value the schema already accepts is left alone. A field typed `union([boolean(), string()])` keeps `'true'` as a string.
- A value that cannot be converted still fails. `NUXT_PUBLIC_REPLAY_ENABLED=maybe` is an error, not `false`.
- Nitro 2 turns `NUXT_VERSION=1.10` into the number `1.1`. The original spelling is gone, so a `string` field rejects it rather than guessing `'1.1'`.
- In a union of objects, a branch whose literal fields contradict the value, such as `kind: 'a'`, is skipped.

The module writes the converted values back into the per-request config on Nitro 2 and the shared config on Nitro 3. Code that still calls `useRuntimeConfig(event)` sees them too.

## Transform values with a schema module

Coercion only fixes types. To parse, normalize or derive values, move the schema into its own file and default-export it:

```ts [runtime-config.schema.ts]
import * as v from 'valibot'

export default v.object({
  allowedOrigins: v.pipe(
    v.string(),
    v.transform(value => value.split(',').map(origin => origin.trim())),
  ),
  public: v.object({
    apiBase: v.pipe(v.string(), v.url(), v.transform(url => url.replace(/\/$/, ''))),
  }),
})
```

Point `$schema` at the file, relative to the project root:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: './runtime-config.schema',
    validateAtRuntime: true,
  },
})
```

The server runs the original schema once after Nitro applies overrides, and `useSafeRuntimeConfig()` returns its output, so `allowedOrigins` is a `string[]`. Transformed `public` values reach the client payload. The [generated types](/guide/type-safety) switch to the schema's output type.

The module still derives a JSON Schema for coercion when it can. Schemas with transforms usually have none, so they receive the raw values, including Nitro 2's parsed numbers and booleans, and must accept both:

```ts [runtime-config.schema.ts]
const runtimeBoolean = v.pipe(
  v.union([v.boolean(), v.picklist(['true', 'false'])]),
  v.transform(value => value === true || value === 'true'),
)
```

Keep parsing in the schema. Code that reads the config should not repeat `value === true || value === 'true'`.

### Asynchronous schemas

Asynchronous schemas work. Request handlers and Nuxt rendering wait for the result. Nitro runs startup plugins synchronously, so a server plugin that reads `useSafeRuntimeConfig()` during initialization needs a synchronous schema.

## Request-scoped config

On Nitro 2, `useRuntimeConfig(event)` is a per-request copy. Platforms such as Cloudflare Workers resolve environment variables per request. `useSafeRuntimeConfig(event)` is its validated counterpart:

```ts [server/utils/cube-token.ts]
import type { H3Event } from 'h3'

export function createCubeToken(event: H3Event): string {
  const { cubeJwtSecret } = useSafeRuntimeConfig(event)
  return jwt.sign({ sub: 'basic' }, cubeJwtSecret, { expiresIn: '1d' })
}
```

When a request has the same values as startup, as it always does on a Node server, it gets a copy of the startup result and the schema does not run again. Otherwise its config is coerced and validated once per request. On Nitro 3, which has one process-wide config, `useSafeRuntimeConfig(event)` returns the same object as `useSafeRuntimeConfig()`.
