::warning

::

Most apps already keep a `.env.example` listing every variable. With `envSchema`, that file becomes the schema. Each entry declares a runtime config key, its type, whether it is required, and whether the browser may see it. No `runtimeConfig` block and no schema library are needed.

Use it when every value comes from the deployment environment and the build must not need secrets. Use [`$schema`](/guide/installation) instead for transforms, custom types, optional nested properties, cross-field rules or computed defaults. An app uses one source, not both.

::steps

### Annotate the file

```dotenv [.env.example]
# Database connection injected when the server starts.
# @type=url @example="postgresql://example.test/database"
NUXT_DATABASE_URL=

# @type=string(minLength=16)
NUXT_API_SECRET=

# @public @type=boolean
NUXT_PUBLIC_REPLAY_ENABLED=false

# @public @type=number(min=0, max=1)
NUXT_PUBLIC_SAMPLE_RATE=0.1

# @public @type=enum(debug, info, warn, error)
NUXT_PUBLIC_LOG_LEVEL=info

# @optional @type=number
NUXT_REQUEST_LIMIT=
```

Everything is required and private unless marked otherwise. An assignment such as `=false` is a real default. `KEY=` declares no default. `@example` is documentation only.

### Point the module at it

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-safe-runtime-config'],
  safeRuntimeConfig: {
    envSchema: '.env.example',
  },
})
```

### Read typed values

```ts
const config = useSafeRuntimeConfig()
config.databaseUrl // string
config.public.replayEnabled // boolean
config.public.sampleRate // number
config.public.logLevel // 'debug' | 'info' | 'warn' | 'error'
config.requestLimit // number | undefined
```

Types come from the declarations during `nuxt prepare`. Local `.env` values are never read for types.

::

::caution
Review an existing `.env.example` before enabling this. A placeholder written as `NUXT_API_SECRET=changeme` becomes a real default that ships in the build. Move placeholders to `@example`.
::

`envSchema` always validates at runtime and skips build validation. Setting `validateAtRuntime: false` is an error. Keep `onError` at `'throw'` so an invalid deployment fails to start.

The [env-spec profile](/schemas/env-spec) defines every decorator, type and default rule.

## Deploy one build with different values

Build with the schema file present and no deployment variables. Start the built server with canonical `NUXT_*` variables:

```bash
NUXT_DATABASE_URL=postgresql://db.internal/app \
NUXT_API_SECRET=a-long-production-secret \
NUXT_PUBLIC_REPLAY_ENABLED=true \
node .output/server/index.mjs
```

The same artifact can start again with other credentials and public settings, no rebuild.

The schema owns the config paths it declares. Values set in `runtimeConfig` or inherited from the build environment at those paths do not become defaults, so a credential present in CI never ends up in the artifact. Assignment defaults are bundled, so keep credentials blank in the file.

## Public and private keys

A key reaches the browser only if it starts with `NUXT_PUBLIC_` and is marked `@public` (or `@sensitive=false`). A `NUXT_` key marked `@public` stays private, because the annotation cannot override Nuxt's prefix rule.

## Nested config

Keys map to flat camelCase fields, so `NUXT_DATABASE_URL` becomes `databaseUrl`. To keep an existing nested shape, map keys to paths:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    envSchema: {
      file: '.env.example',
      paths: {
        NUXT_PUBLIC_POSTHOG_REPLAY_SAMPLE_RATE: 'public.posthog.replaySampleRate',
      },
    },
  },
})
```

Each path must convert back to exactly its declared key, the way Nuxt maps `NUXT_*` variables. Reserved keys, duplicate paths, a path that is both a value and an object, and paths that change visibility fail with the file and line.

Editing the schema file in development restarts Nuxt.

## Arrays and objects

Declare JSON values with item and property types, and quote JSON defaults:

```dotenv [.env.example]
# @type=array(enum(read, write))
NUXT_ROLES='["read"]'

# @type=object(enabled=boolean, retries=number(min=0), tags=array(string))
NUXT_SETTINGS='{"enabled":false,"retries":3,"tags":[]}'
```

`config.roles` is `('read' | 'write')[]`. `config.settings` requires exactly `enabled`, `retries` and `tags`. Bare `array` and `object` accept any JSON array or object. The module validates JSON members as written, so `"false"` inside JSON stays a string and fails a `boolean` property.

## How values are converted

String inputs keep their exact spelling. `NUXT_ACCOUNT_PIN=00123` declared as a string is `'00123'` after startup, although Nitro 2 alone would parse it as `123`. On platforms that build each request's config themselves, a spelling the platform already parsed away cannot be recovered. A value that is present but invalid fails validation; it never falls back to the default. `process.env` keeps its usual `string | undefined` types, and `useRuntimeConfig()` keeps the types Nuxt infers from defaults. Only `useSafeRuntimeConfig()` has the declared types.
