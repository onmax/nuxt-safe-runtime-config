[ViteHub Env](https://vitehub.dev/docs/env) (`vite-hub/env`) replaces runtime config on Nuxt 5 instead of checking it. If you want to keep runtime config, see [Nuxt 5](/guide/nuxt-5) instead. With Env you still declare each value once and read it typed. The differences:

- Server code reads `useServerEnv(event)` and app code reads `usePublicEnv()`, and the same API works in Vite and Nitro apps.
- A secret is a `SecretEnv` that prints `<redacted>` until you call `.unseal()`.
- Env reads the same [`.env.example` format](/reference/env-spec), so an `envSchema` app keeps its file as it is.
- `vitehub env check` lists every declared variable and whether it is set, without printing values.

## Before you start

Use releases of `@vite-hub/codemods` and `vite-hub` that support the migration below. If the published codemod still requires Node.js 24.15 or lacks the Nitro 3 migration, or `vite-hub` doesn't export `vite-hub/env/vite`, keep this module and wait for compatible releases before running the commands.

- **Nuxt 5.** The codemod adds `vite-hub/nuxt`, which needs Nuxt 5. When `package.json` requires an older Nuxt, the codemod stops and writes nothing, also with `--dry-run`. Add `--nuxt-nightly` to set `"nuxt": "npm:nuxt-nightly@5x"` and migrate in the same run. Nuxt 5 stops auto-importing Nitro helpers such as `defineEventHandler` in server code. Set `experimental: { nitroAutoImports: true }` to keep them, or import them.
- **Node.js.** The codemod runs on Node.js 22.12 or later. The migrated app needs Node.js 24.15 or later, because `vite-hub` does.

## Run the codemod

::steps

### Preview the changes

```bash
npx @vite-hub/codemods nuxt-safe-runtime-config --dry-run
```

`--dry-run` prints the diff for each file and the report, and writes nothing. Pass a directory as the last argument when the app isn't in the current one.

### Apply them

```bash
npx @vite-hub/codemods nuxt-safe-runtime-config
```

### Install and check

```bash
pnpm install
```

On Nuxt, run `npx nuxi prepare`. On standalone Nitro 3, run `npx vite build` to generate the Env types.

Then run your typecheck and work through the [follow-ups](#follow-ups) in the report.

::

## What the codemod changes

In `nuxt.config.ts` it replaces `nuxt-safe-runtime-config` with `vite-hub/nuxt` in `modules`, moves your declarations to `vitehub.env` and removes `safeRuntimeConfig`. In `package.json` it removes this module and adds `vite-hub`.

The codemod keeps an explicit `vitehub.host`. Without one, it maps a supported literal `nitro.preset` to a host and sets `node` only if there is no preset. An unsupported literal preset such as `'aws-lambda'` leaves the host unset and adds a follow-up to the report. A computed preset such as `process.env.NITRO_PRESET` stops the migration.

### An `envSchema` app

The `.env.example` stays as it is. `prefix: 'NUXT_'` keeps the variable names and the same public split:

```ts [nuxt.config.ts]
import { envSchema } from 'vite-hub/env/vite'

export default defineNuxtConfig({
  modules: ['vite-hub/nuxt'],
  vitehub: {
    host: 'node',
    env: envSchema(new URL('./.env.example', import.meta.url), { prefix: 'NUXT_' }),
  },
})
```

### A `$schema` app

The codemod loads your schema, converts it to JSON Schema and writes one Env declaration per value. Each value keeps its `NUXT_*` name. Env reads the name `VITEHUB_<PATH>` first, such as `VITEHUB_API_SECRET` before `NUXT_API_SECRET`.

The codemod can keep field schemas for lengths, patterns, formats, refinements, transforms, and JSON arrays or objects. It exports the retained schemas from `server/env.schema.ts`. Server fields run them with `env.schemaFrom()` when the server reads the value. Public fields import them into `nuxt.config.ts`, and Env runs them during the build.

::code-group

```ts [Before]
export default defineNuxtConfig({
  modules: ['nuxt-safe-runtime-config'],
  runtimeConfig: {
    apiSecret: '',
    maxRetries: 3,
    featureEnabled: false,
    public: { apiBase: 'https://api.example.com' },
  },
  safeRuntimeConfig: {
    $schema: v.object({
      apiSecret: v.pipe(v.string(), v.minLength(16)),
      maxRetries: v.number(),
      featureEnabled: v.boolean(),
      public: v.object({ apiBase: v.pipe(v.string(), v.url()) }),
    }),
  },
})
```

```ts [After]
import { env } from 'vite-hub/env'
import { publicApiBase } from './server/env.schema'

export default defineNuxtConfig({
  modules: ['vite-hub/nuxt'],
  vitehub: {
    host: 'node',
    env: {
      public: {
        apiBase: env({ default: 'https://api.example.com', mode: 'build', schema: publicApiBase, source: env.source('NUXT_PUBLIC_API_BASE') }),
      },
      server: {
        apiSecret: env({ schema: env.schemaFrom('./server/env.schema.ts', 'apiSecret'), secret: true, source: env.source('NUXT_API_SECRET') }),
        maxRetries: env.number({ default: 3, source: env.source('NUXT_MAX_RETRIES') }),
        featureEnabled: env.boolean({ default: false, source: env.source('NUXT_FEATURE_ENABLED') }),
      },
    },
  },
})
```

```ts [server/env.schema.ts]
import * as v from 'valibot'

const runtimeConfigSchema = v.object({
  apiSecret: v.pipe(v.string(), v.minLength(16)),
  maxRetries: v.number(),
  featureEnabled: v.boolean(),
  public: v.object({ apiBase: v.pipe(v.string(), v.url()) }),
})

export const apiSecret = runtimeConfigSchema.entries.apiSecret
export const publicApiBase = runtimeConfigSchema.entries.public.entries.apiBase
```

::

Literal defaults stay. The codemod checks each default against the field's schema first. `apiSecret: ''` fails `minLength(16)`, so the module stopped the app when `NUXT_API_SECRET` wasn't set. The codemod keeps no default, and Env requires `NUXT_API_SECRET` too. A secret keeps no default other than `''`, because defaults are written into the server build.

Server fields with credential-like names, such as `secret`, `token`, `password`, `key` or a database URL, become `secret: true`.

The report distinguishes fields that move without a check from fields that stay in `runtimeConfig`. For example, with `onError: 'warn'`, a string such as `region` with `v.minLength(3)` moves to Env without the length check. If you still need warning-only validation, add it where the migrated value is read.

Examples of fields that stay in `runtimeConfig`:

- Its default comes only from the schema, such as `v.optional(schema, 'x')` or `.default('x')`. Env doesn't run the schema when the variable isn't set.
- Its value in `runtimeConfig` is computed, such as `['a', String(1)]`.
- Its schema is async. Server Env runs schemas synchronously.
- It is a union of input types, or the codemod can't export its schema.

The codemod stops and writes nothing when the module options have a spread, a computed key or a repeated key, because it can't tell which `$schema` the module used.

### Your code

```ts [server/api/config.get.ts]
// Before
const config = useSafeRuntimeConfig(event)

// After
import { useServerEnv } from 'vite-hub/env'
const config = useServerEnv(event)
```

In app code, `useSafeRuntimeConfig()` becomes `usePublicEnv()` from `#vitehub/env/public`, and `config.public.apiBase` becomes `config.apiBase`.

::warning
Env fixes public values at build time. This module applied `NUXT_PUBLIC_*` overrides when the server started, so set those variables before you build. Server values are still read when the server runs. [vite-hub/vitehub#5428](https://github.com/vite-hub/vitehub/issues/5428) tracks public values that change at runtime.
::

## Follow-ups

The report lists each change the codemod couldn't make, with its `file:line`:

- `config.apiSecret` is now a `SecretEnv`. Call `.unseal()` where the code needs the raw value.
- A number or boolean field that keeps its schema reads its variable as JSON. Spellings such as `0xBB8`, `+3000`, `.5`, `1`, `0` or `TRUE` now fail.
- With `validateAtRuntime: false`, the module checked the schema only at build. Env runs it when the server reads the value.
- A rule on the whole object, such as a cross-field check, doesn't carry. Check it in server code.
- Review reported checks that were dropped from migrated fields and restore any validation you still need.
- Each field that stayed in `runtimeConfig`. Read it with `useRuntimeConfig()`, or move it to Env by hand.
- If the report flags an unsupported `nitro.preset` and leaves `vitehub.host` unset, configure a supported host before deploying. If neither a preset nor an explicit host was set, the codemod generates `node`; change it if you deploy elsewhere.
- Calls it couldn't follow, such as a config object passed to another function, or a `useRuntimeConfig()` read of a key that moved.
- `nuxt-safe-runtime-config/eslint` in your ESLint config, which you remove by hand.

## A Nitro app

The same command moves a Nitro 3 app (the `nitro` package) that uses the [Nitro module](/guide/nitro):

- It writes `vite.config.ts` with `vitehub({ host, env })` before `nitro()` from `nitro/vite`. If the app has a `vite.config`, it adds `vitehub()` to its `plugins`.
- Migrated fields are Server Env only. There is no Public Env in the standalone Nitro migration.
- It rewrites `useRuntimeConfig()` from `nitro/runtime-config` to `useServerEnv()` from `vite-hub/env` when the call reads only migrated keys. It adds `.unseal()` to each secret read, so the code keeps the raw value.
- It removes the module, `safeRuntimeConfig` and the migrated keys from `nitro.config.ts`. `nitro()` still reads that file, so the other options stay.
- In `package.json` it swaps this module for `vite-hub`, adds `vite`, and changes `nitro dev` and `nitro build` to `vite dev` and `vite build`.

Env checks the canonical `VITEHUB_*` name before the explicit `NITRO_*` name in `env.source()`. For example, if both `VITEHUB_GREETING` and `NITRO_GREETING` are set, `VITEHUB_GREETING` wins. Overrides using Nitro's `_` prefix or a custom `NITRO_ENV_PREFIX` do not carry over automatically.

The codemod stops and writes nothing on a Nitro 2 app (`nitropack`). Keep `nuxt-safe-runtime-config/nitro` while the app runs on Nitro 2.
