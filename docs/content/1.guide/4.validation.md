The module validates your runtime config to catch configuration errors early. By default, validation runs at build time only.

Choose one place for validation to be authoritative:

- **Build validation** checks the values written in `nuxt.config.ts`. Use it when those values ship unchanged.
- **Runtime validation** checks the values the deployed server actually runs with, after Nitro applies environment overrides. Use it when secrets or flags come from the deployment environment.

Enabling `validateAtRuntime` turns build validation off by default, because build-time values are only placeholders for what the environment supplies. Set `validateAtBuild: true` to keep both. The same default applies to the standalone Nitro module (`safeRuntimeConfig` in `nitro.config.ts`).

Validation is handled by the package's Nitro module. In Nuxt apps, the Nuxt module exposes the user-facing API, types, and imports, then passes validation options into Nitro. Generated validation files are internal implementation details and their paths are not part of the public API.

## Build-time Validation (Default)

With default settings, build validation runs through Nitro during:

- **Dev start** - when running `nuxt dev`
- **Build** - when running `nuxt build`

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
    validateAtBuild: true, // default unless validateAtRuntime is enabled
  },
})
```

Build-time validation uses your schema library directly. It catches:

- Missing required values
- Type mismatches
- Invalid formats

Inline schemas provide these build-time benefits:

- Zero runtime overhead
- Fail fast before deployment
- CI/CD friendly
- The validation library does not need to run in production

## Runtime Validation (Opt-in)

Runtime validation catches issues that only appear in production, such as environment variables that differ from their build-time values. Inline schemas retain JSON Schema validation:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
    validateAtRuntime: true,
    onError: 'throw',
  },
})
```

When you enable runtime validation with an inline schema, the module:

1. Generates JSON Schema from your Standard Schema.
2. Coerces environment overrides against that JSON Schema.
3. Validates `useRuntimeConfig()` through a Nitro plugin on cold start.
4. Uses [@cfworker/json-schema](https://github.com/cfworker/cfworker/tree/main/packages/json-schema), an edge-compatible runtime validator.

JSON Schema describes and validates data shapes, but it cannot execute Standard Schema transformations. Use a schema module when runtime input and validated output have different types beyond the coercions below.

## Environment Coercion

Environment variables are strings. Nitro 3 passes them to runtime config unchanged, and Nitro 2 parses only some of them (`NUXT_FLAG=1` becomes the number `1`). With runtime validation enabled, the module converts an override to the type the schema expects before validating it:

| Schema expects  | Converted values                                                   |
| --------------- | ------------------------------------------------------------------ |
| `boolean`       | `'true'`, `'false'`, `'1'`, `'0'` (any case), `1`, `0`             |
| `number`        | numeric strings such as `'0.5'` or `'3000'`                        |
| `integer`       | integral strings such as `'3000'`                                  |
| `string`        | integers and booleans that Nitro 2 parsed, such as `123` or `true` |
| array or object | JSON strings such as `'["email","github"]'`                        |
| enum or literal | strings that convert to one of the allowed values                  |

Coercion only touches values the schema would otherwise reject. Strings stay strings wherever the schema accepts a string, including `union([boolean(), string()])`. Values that cannot be converted, such as `NUXT_PERF_TRACE_ENABLED=maybe`, still fail validation. Nitro 2 turns `1.10` into the number `1.1`, which can't be turned back into the original string, so a non-integral number for a `string` field fails validation too. For unions of objects, a branch whose literal fields (such as `kind: 'a'`) contradict the value is skipped.

The validated values are written back into runtime config objects that Nitro lets the module change: the per-request `useRuntimeConfig(event)` on Nitro 2, and the shared config on Nitro 3. Code that reads `useRuntimeConfig(event)` then sees the converted values too. That is how Nuxt's server render, SPA render (`ssr: false`), and prerender serialize them into the client payload.

A plain schema is then enough, and consumers read real booleans and numbers on the server and in the client payload:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  runtimeConfig: {
    perfTrace: { enabled: false },
    public: { posthog: { enabled: false, replaySampleRate: 0.1 } },
  },
  safeRuntimeConfig: {
    $schema: object({
      perfTrace: object({ enabled: boolean() }),
      public: object({ posthog: object({ enabled: boolean(), replaySampleRate: number() }) }),
    }),
    validateAtRuntime: true,
  },
})
```

Schema modules are coerced against their input JSON Schema when the module can derive one. Schemas that use transforms often have no JSON Schema form. They receive the raw values, including Nitro 2's parsed numbers and booleans, and must do their own parsing, as shown below.

## Transform Runtime Values

Use a schema module when runtime values need parsing beyond the built-in coercions. Define it once so every consumer receives the same validated output:

```ts [runtime-config.schema.ts]
import * as v from 'valibot'

const runtimeBoolean = v.pipe(
  v.union([v.boolean(), v.picklist(['true', 'false'])]),
  v.transform(value => value === true || value === 'true'),
  v.boolean(),
)

const runtimeNumber = v.union([
  v.number(),
  v.pipe(v.string(), v.decimal(), v.transform(Number), v.number()),
])

export default v.object({
  perfTrace: v.object({
    enabled: runtimeBoolean,
    token: v.string(),
  }),
  public: v.object({
    posthog: v.object({
      enabled: runtimeBoolean,
      replaySampleRate: runtimeNumber,
    }),
  }),
})
```

Reference the module from `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: './runtime-config.schema',
    validateAtRuntime: true,
  },
})
```

The module executes the original Standard Schema once after Nitro applies runtime overrides. Asynchronous schemas finish before request handlers run, server-side `useSafeRuntimeConfig()` returns `result.value`, and Nuxt serializes transformed `public` values into the client payload.

Nitro startup plugins run synchronously. Use a synchronous schema when reading `useSafeRuntimeConfig()` during plugin initialization; asynchronous schemas are ready from request handlers and Nuxt rendering onward.

## Event-scoped Config

Pass the request event to read the validated equivalent of `useRuntimeConfig(event)`:

```ts [server/utils/cube-auth.ts]
import type { H3Event } from 'h3'

export function createCubeAuthToken(event: H3Event): string {
  const { cubeJwtSecret } = useSafeRuntimeConfig(event)
  return jwt.sign({ sub: 'basic' }, cubeJwtSecret, { expiresIn: '1d' })
}
```

The validation middleware prepares each request's config before handlers run. When it has the same values as the startup config, which is always the case on Node servers, the request gets its own copy of the startup result and the schema does not run again. Platforms that resolve environment per request get the request's config coerced and validated once per request. The return type is the same as `useSafeRuntimeConfig()`.

Nitro 3 has no per-request runtime config: its `useRuntimeConfig()` returns one process-wide object. There, `useSafeRuntimeConfig(event)` returns the same validated config as `useSafeRuntimeConfig()`.

Consumers can use the canonical output directly:

```ts [server/plugins/perf-trace.ts]
const config = useSafeRuntimeConfig()

if (config.perfTrace.enabled)
  startTracing()
```

Keep parsing and normalization inside the schema module. Consumer code should not accept both raw and transformed types or repeat checks such as `value === true || value === 'true'`.

Shelve runtime fetching remains a separate integration. When `shelve.fetchAtRuntime` is enabled, that runtime fetch plugin runs before validation so fetched secrets can be validated.

What it catches:

- Missing env vars in production (`DATABASE_URL` not set)
- Type mismatches (`NUXT_PORT=abc` when expecting number)
- Invalid values at runtime

## Error Handling

Use `onError` to control how both build-time and runtime validation errors are handled:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: runtimeConfigSchema,
    onError: 'throw', // 'throw' | 'warn' | 'ignore'
  },
})
```

- **`'throw'`** (default) - stops the build; runtime validation stops server startup for synchronous schemas and rejects requests for asynchronous schemas or invalid event-scoped config
- **`'warn'`** - logs warning, continues
- **`'ignore'`** - silent

## Error Messages

When validation fails:

```
[safe-runtime-config] Validation failed!
  1. databaseUrl: Invalid type: Expected string but received undefined
  2. public.apiBase: Invalid type: Expected string but received undefined
  3. port: Invalid type: Expected number but received string
```

## Both Modes

Enable both modes when the build-time values must already be valid, for example when CI builds with real values:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  safeRuntimeConfig: {
    $schema: './runtime-config.schema',
    validateAtBuild: true, // opt back in: check nuxt.config values during the build
    validateAtRuntime: true, // check deployed values
    onError: 'throw',
  },
})
```
